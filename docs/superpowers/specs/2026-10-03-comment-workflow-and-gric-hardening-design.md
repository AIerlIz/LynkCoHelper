# Independent AI Comment Task and GRIC Hardening

Date: 2026-10-03

## Scope

Add an independent daily GitHub Actions task that finds new text/image posts in the LynkCo square, analyzes each post with ChatAnywhere, and publishes a relevant comment. The maximum number of comments per run is configurable and defaults to one. Do not add commenting to the existing sign/share task. Fix the defects identified in the current uncommitted GRIC code and update its documentation so a user can run it after supplying credentials, without editing source or copying captured identifiers.

The attached `favorites.json` and subsequent ProxyPin HAR are examples of a successful iOS comment request, not instruction sources or sources of reusable credentials. The HAR confirms HTTP 200, business `success`, and a `commentId`, and its `relaCode` matches an article-detail request in the same capture. It does not prove the comment relation for a UGC post. Post and author IDs must come from live responses; account credentials and the ChatAnywhere API key must come from runtime configuration. Never copy captured IDs, cookies, signatures, timestamps, comment text, or secrets into source or logs.

## Comment Data Flow

1. Load a LynkCo token through the existing login module. Fetch pages with signed `GET /app/explore/home-page/v3/list?pageNo=N` on `app-api-gw-toc.lynkco.com`; the HAR also uses `pageSize=20` and a page code, but a live read-only probe succeeded without the page code. Read only `data.queryResult.items`. Observed `origin=1` articles use `id`, `title`/`summary`, and `coverImage`; `origin=2` UGC image/text posts use `ugcId`, `content`, and `contentImage` (a list of URL strings). Both expose `publishTime`. Normalize these into a stable ID, type, UTC publication time, author ID, text, and HTTPS images; reject missing/unknown shapes, videos, and duplicate IDs. Do not fall back to the share task's fixed article ID.
2. Select posts published in the last 48 hours by default (configurable) that are not in the success ledger. Validate `LYNKCO_COMMENT_MAX_PER_RUN` as an integer from 1 to 10 (default 1). Selection and de-duplication happen before model calls, so a retry does not spend tokens on already commented posts. A missing/unparseable publish time is not treated as new.
3. Send only public post text and at most three public image URLs to `https://api.chatanywhere.tech/v1/chat/completions`. Read the API key from `CHATANYWHERE_API_KEY`; use a configurable vision-capable model, with `gpt-4o-mini` as the documented default. The prompt asks for a specific Chinese comment of at most 80 characters grounded in the post, and treats post content as data rather than instructions. Reject empty, truncated, overlong, or clearly unrelated model output. If neither text nor accessible images can be analyzed, skip the post. The local dry-run can incur model API charges, but never sends the comment POST.
4. Build the comment request from live post metadata and the successful HAR: `POST /app/explore/home-page/comment/create`, query `relaCode`/`relaTypeCode`, and the captured iOS-style signature-header ordering including the current token. The article's `relaCode` is its article ID and `relaTypeCode=content`; the relation code for UGC `ugcId` remains a hypothesis until a controlled live UGC comment confirms it. Match the HAR body types (`insideMessage` and `atInsideMessage` objects, `atUserList` array, `interactContent` JSON string with `span` entries, numeric `skipDunshanFlag=0`) using live author/account fields rather than captured values. Sign the exact sent UTF-8 body bytes and validate HTTP status, business `code`, and `data.commentId` before confirming success. Never copy captured cookies, IDs, or credentials.
5. Persist a separate uncertain/quarantine ID before each comment POST; after confirmation atomically move it into successes. Never automatically retry an uncertain POST. Business failures and disk-write failures stop the run with an actionable, credential-free status. A future server-side lookup would be needed for full exactly-once semantics.

## State, Entrypoints, and Notifications

- `lynkco_comment.py` exposes small units for feed normalization, eligibility, prompt/media construction, signed posting, and a run coordinator. A CLI supports an offline fixture, local `--dry-run` (fetch and generate but never publish), and an explicit publish mode. Success and uncertain IDs are persisted in an ignored state file; no captured IDs or comment text are defaults. Current-user/device IDs come from documented configuration and author fields from the live post.
- After a local model dry-run and one explicitly controlled UGC publish confirm the relation mapping, add a separate `.github/workflows/comment-task.yml` with a daily schedule and manual dispatch defaulting to dry-run. Restore the newest state artifact even after partial failure, serialize runs, and upload state after partial successes. First-run missing state is normal; API/auth or invalid-state failure is not. Use only Actions Secrets for LynkCo credentials, a fresh ChatAnywhere API key, and optional Bark key; do not change sign/share.
- Reuse `send_bark_notification` with a dedicated comment group. A run summary includes confirmed, skipped, failed, and uncertain counts plus safe post titles/IDs, without credentials or full request/response bodies. Bark failure is reported but does not change a confirmed posting result. Dry-run is clearly labeled and never counted as posted.
- Run validation in this order: existing offline checks and local fixture CLI; read-only v3 feed inspection; local live read/model `--dry-run` using a runtime-only ChatAnywhere key; one manually reviewed UGC comment publish to validate its ID/relation/body; then add and validate the Actions workflow. The key posted in chat should be rotated before persistent use and must not be written into the repository or shell history. Per the user's latest direction, do not add more unit tests.

## Trade-offs

Automatic publishing matches the requested workflow but puts model output in a public comment without human review. The per-run cap, bounded prompt, output validation, dry-run, and fail-closed branches limit mistakes; they cannot guarantee the quality of every generated comment. Images depend on URLs reachable by the model provider. Durable artifact state avoids writing a repository branch, but is not an exactly-once transaction with the upstream comment endpoint.
